Checked every 15 minutes from the CircleCI and GitHub APIs by .github/workflows/status.yml. It rewrites status.json only when the results actually change, so no bot commit lands on main just because a check ran. A failed run blocks the pull request, not the download: published images are never replaced by an unfinished build.

Status reporting

How each result reaches your pull request.

Same rules for every KibaOS repository, whether you branch on GitHub or GitLab.

Commit status updates

One status per job, written back to your version control system. Job statuses use the form ci/circleci: <job_name>, so a failing compile is visible on the commit itself — not just at the end of the pipeline. 

ci/circleci: build_kibaos
ci/circleci: package-kibade
ci/circleci: sign-and-publish

Approval and no-op jobs carry their workflow name as well, for example ci/circleci: release/sign-and-publish.

GitHub Checks

Workflow-level results appear in the Checks tab of a pull request, one check per workflow. Re-run a workflow from there, or open it in CircleCI for the job-by-job view. 

KibaOS / build_kibaos
KibaOS / Converge GN evaluation
Website / Deploy Jekyll with GitHub Pages

Checks and commit statuses can both be on at once: the Checks tab shows the workflow, the conversation view shows each job.

GitLab statuses

For GitLab projects, one status is reported per workflow rather than per job. These are always on and cannot be switched off, so merge requests always have a result from the pipeline.

Build badge for your README

If you package KibaOS or build KibaDE, you can show the current state of the default branch next to your own project. 

[![KibaOS build](https://circleci.com/gh/KibaLabsLLC/KibaOS.svg?style=shield)](https://kibaos.com/status.html)

The badge reflects the default branch only. A red badge on your project with a green one here usually means a stale fork.

Naming and behaviour follow CircleCI's status updates documentation, including the ci/circleci: prefix and workflow-level Checks.
